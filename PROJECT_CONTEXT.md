# DataFlow — контекст проекта

## Что строим

Schema-aware visual data workflow platform: источники → понимание структуры данных → преобразования → проверка → получатели → наблюдение. Пользователь выбирает блоки и настройки без написания кода. Платформа хранит конфигурацию, исполняет её асинхронно и объясняет состояние каждого запуска.

Ключевое отличие от generic workflow automation: между узлами передаётся не произвольный JSON, а логический Dataset со schema, records и execution metadata. Аудитория: аналитик собирает данные; разработчик автоматизирует обмен; маркетолог объединяет информацию для анализа. Произвольные production deployment workflows — долгосрочное направление, не MVP.

## Направления из обсуждения

- Laravel — основной API и бизнес-правила; PostgreSQL — данные приложения.
- Vue 3 + TypeScript, Vite, Pinia, Vue Router — интерфейс.
- Node.js + TypeScript — исполнение; Redis — транспорт задач; Docker Compose — локальная среда.
- Модульный монолит с отдельным worker; выделение сервисов только по реальной необходимости.
- Проекты, подключения, графы, запуски и обзор текущих работ.
- S3 исключён из начального списка. AI, MCP, marketplace и SDK отложены.

## Рабочие предложения v0.1

Первый срез: CSV → Filter → Map → CSV, ручной запуск через настоящий Node worker, статус и скачиваемый результат. Данные в runtime описываются как Dataset v1: schema + batch records. В первом срезе schema может быть задана вручную или получена простым inference из заголовков/sample; сложная schema evolution, lineage, streaming и distributed execution отложены.

Полный MVP добавляет PostgreSQL/MySQL/REST, организации с приглашениями и простыми ролями, историю и разветвление данных.

Граф MVP — DAG с одним источником; у остальных узлов ровно один вход. Возможны несколько выходящих связей, но без Join, циклов и параллельного исполнения. Запуск хранит неизменяемый снимок графа. Новое сохранение не меняет уже запущенную работу.

Laravel — единственный писатель в БД приложения. Предлагаемый транспорт: Redis Streams с JSON-сообщением, transactional outbox в PostgreSQL, internal API для claim/heartbeat/events. Подробности и гарантии находятся в [WORKER_PLAN](docs/WORKER_PLAN.md). Нельзя незаметно заменить этот протокол Laravel Queue/BullMQ.

## Текущее состояние

Завершены M0/T01 и foundation T02–T03. Помимо исходного каркаса с Laravel, Vue, worker, Docker Compose, PostgreSQL, Redis и gateway, backend теперь содержит session/CSRF authentication через Sanctum, users, organizations, memberships и projects. Регистрация атомарно создаёт пользователя, personal organization и owner membership. Роли `owner`, `editor`, `viewer` существуют в membership; управление участниками и invitations намеренно отложены.

Реализованы `register`, `login`, `logout`, `/me`, tenant-scoped CRUD проектов и архивирование. Laravel проверяет membership для organization и повторно ограничивает каждый nested project выбранной organization; чужие ресурсы скрываются ответом 404, viewer не может изменять или архивировать. API использует success/error envelopes и server-generated `request_id`. Factories и безопасный seed создают две demo-организации; реальные demo-пользователи создаются только явным локальным seed без попадания паролей или других секретов в репозиторий.

Фактически проверены: прежние проверки T01, а также `docker compose exec backend php artisan test` — 13 passed, 48 assertions с заявленной настройкой `dataflow_test`; позднее выявлено, что окружение контейнера могло направлять эти тесты в основную базу. Набор покрывает регистрацию с personal organization/owner membership, login, `/me`, logout, создание и валидацию проектов, tenant isolation через чужой nested ID, недостаточную роль viewer и архивирование. Команды запуска, остановки и тестов находятся в [README](README.md).

Завершён T04 frontend foundation: Vue Router и Pinia обеспечивают session/CSRF browser auth, получение `/me`, выбор доступной организации, защищённые маршруты и очистку project state при смене organization. Реализованы login/register, список, создание, загрузка и редактирование проектов через существующий API; viewer получает понятное состояние «только просмотр». Dashboard честно сообщает об отсутствии Execution API. В браузер не попадают secrets; API-клиент перед mutating requests получает Sanctum CSRF cookie и передаёт только decoded XSRF token. Frontend использует закреплённый Prettier с tab indentation; доступны `npm run format` и `npm run format:check`. Локальный idempotent demo seed создаёт указанного в `.env` пользователя как owner всех существующих организаций и owner/editor/viewer в учебной организации; пароль нужен только в локальном `.env`.

Фактически проверены: `npm run format:check`, `npm run type-check`, `npm run build`, `docker compose up --build -d backend`, проверка CSRF-cookie (`204`), guest `/me` (`401`), `docker compose exec gateway nginx -t` и `docker compose exec backend php artisan test` — 13 passed, 48 assertions. Интерактивная browser-проверка недоступна из-за сбоя sandbox browser helper; её нужно выполнить локально. Ограничения этапа: нет invitations/member management, connections, assets, Dataset/DataSchema, pipelines, graph validation, executions, Redis Streams и runtime worker. Следующий этап: UI builder T06, затем assets и runtime.

## T05 — pipeline и graph API

Реализованы модели Pipeline/Node/Edge с PostgreSQL ограничениями принадлежности проекту и организации, каталог четырёх типов и API создания, чтения, переименования, архивирования, сохранения и проверки графа. Запись заменяет граф атомарно и проверяет revision. Сервер проверяет форму, allowlist конфигурации, типы и версии узлов, порты, циклы, дубликаты и известные поля schema. Неполный draft разрешён; validate проверяет полноту и сообщает об неизвестной schema. Договоры Dataset/DataSchema/graph и примеры лежат в `contracts/`. См. [API_DRAFT](docs/API_DRAFT.md).

На момент T05 хранилища файлов и runtime ещё не было: resolver по умолчанию отвергал любой asset ID. На T07 подключено хранилище. Тесты используют явную подмену resolver. Каталог не обещает работающие обработчики; executions API отсутствует. После подключения assets понадобится повторная проверка их принадлежности и готовности при запуске.

Фактически проверены форматирование изменённых PHP-файлов и полный набор backend-тестов: 23 теста, 104 assertions. Среди них tenant isolation, роль viewer, revision conflict, rollback при ошибке вставки, некорректные графы и schema propagation. Следующий этап — T06 UI builder, затем assets/runtime; интерфейс запуска пока недоступен.

## T06 — визуальный редактор

На странице проекта можно создавать и открывать потоки. Редактор на Vue Flow показывает каталог типов из API, canvas с сохранением позиции, настройки узлов и форму соединения как альтернативу перетаскиванию. Фильтр и сопоставление используют известные поля schema или позволяют ввод вручную при неизвестной структуре; CSV source поддерживает ручное описание полей. Черновик сохраняется с revision, выводятся ошибки сервера и предупреждение при конфликте; локальные изменения не перезаписываются автоматически. Роль viewer получает режим просмотра. Реальной загрузки файлов и запуска пока нет.

Проверены `npm run build` (включая type-check), `npm run format:check`, `npm audit` после обновления двух транзитивных зависимостей. В локальном браузере на временных данных пройден сценарий создать проект и поток → добавить четыре узла → соединить → сохранить → перезагрузить → изменить в двух окнах и получить конфликт. Проверено появление вручную заданного поля в фильтре. Временные записи удалены. Следующий этап — T07 assets, затем runtime; ручная проверка доступности и drag-and-drop в других браузерах остаётся полезной.


## T07 — входные CSV и защита тестовой базы

Доступны загрузка, список и авторизованное скачивание CSV в организации; файлы хранятся в приватном volume с пределом 10 МиБ по умолчанию. Сервер при сохранении и проверке графа принимает только готовый файл своей организации. В редакторе можно выбрать файл и сохранить ссылку в графе. Исполнение, повторная проверка файла при запуске и очистка файлов после аварийного прерывания ещё не реализованы.

Фактически проверены 25 backend-тестов (128 assertions), сборка и форматирование frontend; в отдельной временной базе в браузере проверены выбор готового CSV, сохранение и повторное открытие графа. Отправка файла через кнопку браузера отдельно не проверена.

При предыдущем запуске тестов выяснилось, что переменные окружения контейнера перекрывали параметры PHPUnit: миграции очистили основную локальную базу `dataflow`. Резервная копия не найдена. Добавлена защита, которая до любых тестовых миграций проверяет фактическое подключение к `dataflow_test`; после этого тесты повторно прошли на отдельной базе. Следующий шаг — проверка браузерной загрузки и реализация устойчивого намерения запуска и снимка графа по [WORKER_PLAN](docs/WORKER_PLAN.md).


## Первое исполнение — контрольный результат A (намерение запуска)

Созданы Execution, ExecutionNode, ExecutionLog и outbox. Owner/editor может через API создать queued запуск с UUID ключом и revision; Laravel блокирует организацию, проект и pipeline, повторно проверяет готовность графа и CSV и атомарно сохраняет снимок, pending узлы и минимальное сообщение. Повтор ключа возвращает тот же запуск, другая операция с тем же ключом — 409; уникальный индекс защищает от двух активных запусков. Архивирование проекта и pipeline с активными запусками запрещено. Viewer может читать историю конкретного запуска в своей организации.

Фактически проверены 29 backend-тестов (176 assertions) на `dataflow_test`, включая tenant isolation, права, повтор ключа, неизменность снимка, rollback outbox и ограничение активного запуска в PostgreSQL. Одновременные HTTP-запросы отдельно не проверялись. Worker, dispatcher Redis, lease/events, watchdog, исполнение и UI запуска отсутствуют; прямой API-запрос остаётся queued. Следующий шаг — контракт транспорта Redis Streams и internal API согласно [WORKER_PLAN](docs/WORKER_PLAN.md).


## Первое исполнение — транспортный контракт

Подготовлены JSON Schema и фикстура минимального Redis envelope, PHP publisher с проверкой допустимых полей и Node parser. Клиент `redis` закреплён на версии 5.8.3. Добавлены локальные тесты parser и тестовый сценарий PHP → Redis Stream → Node consumer с двумя копиями сообщения и TTL отдельного тестового потока. Этот сценарий не включает реальное исполнение и не связан с outbox dispatcher.

Фактически проверены PHP → настоящий Redis Stream → Node consumer (две одинаковые доставки), worker build и 2 теста, полный backend набор — 35 тестов, 182 assertions на dataflow_test. Проверка транспорта не осуществляет claim и не запускает граф. Следующий шаг — dispatcher outbox, затем claim/lease/events и worker runtime.


## Первое исполнение — отправитель outbox (часть результата B)

Добавлен ограниченный dispatcher: он блокирует непубликованную запись с `SKIP LOCKED`, сверяет идентификаторы envelope с записью, публикует её и помечает результат. Ошибки записи в Redis приводят к отложенному повтору с ограниченной задержкой; если подтверждение потерялось, повторяется тот же message_id. Соединение с Redis ограничено по времени. Команда однократной обработки существует, но расписание и автоматический запуск отключены до появления worker claim и восстановления после потери Redis.

Фактически полный backend-набор прошёл на dataflow_test: 39 тестов, 205 assertions, включая Redis integration в отдельном потоке и повтор после потери подтверждения; отдельно проверен PHP → Redis → Node контракт. Одновременный запуск нескольких dispatcher ещё не проверен. Claim/lease/events, reconciler, watchdog и CSV runtime остаются следующими шагами.

Для следующего этапа добавлена внутренняя основа lease запуска и миграция; она пока не подключена к worker или HTTP API. Отправка outbox и обработка истёкших запусков автоматически не запускаются. Подробности и оставшиеся требования — в `docs/WORKER_PLAN.md`.

## Internal claim и heartbeat

Backend предоставляет защищённые сервисным токеном `/internal/v1/executions/{id}/claim` и `/heartbeat`. Claim повторно проверяет снимок и ready asset своей организации; повтор после потери ответа не выдаёт новый lease. Контракт форматов и примеры находятся в `contracts/`. Тесты: 45 passed, 252 assertions на отдельной PostgreSQL и Redis. Watchdog, события, reconciler и worker runtime пока не подключены; конкурентные вызовы не проверены.

## События выполнения

Внутренний API принимает упорядоченные события начала, успеха и ошибки узла и ошибочного завершения запуска. Идентичный повтор подтверждается без повторного изменения данных, неверная последовательность, чужой или просроченный lease отклоняются. Успешное завершение CSV-получателя и запуска пока не поддерживается до сохранения готового результата. Фактически проверено 48 backend-тестов, 283 assertions, включая изолированные PostgreSQL и Redis; конкурентные запросы к events отдельно не проверялись. Следующий шаг — доступ worker к исходному файлу и безопасное сохранение результата.

## Входной файл worker

Internal API отдаёт поток исходного CSV только worker с действующим lease, если файл указан в snapshot и готов в организации запуска; проверяется размер. Выдача результата пока не реализована. Следующий этап — сохранение и авторизованное получение итогового CSV.

## CSV результат worker

Worker с действующим lease может загрузить результат работающего CSV destination потоком до 10 МиБ с проверкой SHA-256. Организация и имя определяются сервером из запуска; готовый asset привязан к execution/node, а повтор идентичной загрузки возвращает тот же ID. Частичный файл не получает запись ready; при аварии процесса возможен неучтённый файл. Успешное завершение запуска и runtime worker ещё не подключены.

Проверено 53 backend-теста, 321 assertion на отдельной PostgreSQL и Redis, включая повтор загрузки, checksum, лимит и tenant isolation при скачивании. Параллельные загрузки и аварийное завершение процесса отдельно не проверены.

## Успешное завершение запуска

Internal events позволяют подтвердить успешный destination только при готовом файле с верным размером и SHA-256; запуск завершается успешно только после всех узлов и проверки результатов. Повтор финального события подтверждается без повторного изменения данных. Участник организации видит metadata результата в API запуска. Реальное исполнение Node worker и автоматическая доставка ещё не включены.

Проверено 54 backend-теста, 340 assertions на отдельной PostgreSQL и Redis, включая изменение результата при неизменном размере, повтор финального события и изоляцию организации. Параллельные события и полноценный запуск worker отдельно не проверены.

## CSV runtime worker

Реализованы автономные функции чтения CSV, Filter, Map и записи CSV с ограничениями и безопасными кодами ошибок. Проверены образец из contracts, экранирование, пустой результат, некорректные данные и лимиты: 6 worker-тестов проходят в Docker. Они пока не подключены к Redis consumer или внутреннему API; для работающего запуска ещё нужны orchestration, heartbeat и восстановление.

## Сквозное исполнение в изолированной проверке

Worker связывает claim, последовательное исполнение линейного графа CSV/Filter/Map/CSV, heartbeat, ограниченную загрузку входа, подтверждаемые события и идемпотентную передачу результата. Реальная проверка Laravel → Redis → Node → Laravel на dataflow_test прошла: две одинаковые доставки дали один запуск, девять событий и ожидаемый CSV. Проверено 12 worker-тестов, включая потерю подтверждения и отказ lease. Постоянный consumer, обработка pending/dead-letter, автоматическая публикация, watchdog и reconciler ещё не подключены; UI запуска остаётся отключённым.

## Восстановление запусков

Добавлена ограниченная команда восстановления: истёкший lease завершает работающий запуск с WORKER_LOST без повтора, ожидающий более 30 секунд queued запуск повторно публикуется через outbox с задержкой, а после 10 минут получает QUEUE_TIMEOUT. Потеря Redis проверена на отдельном временном потоке. Команда пока не запускается автоматически; постоянный consumer и обработка pending остаются следующими шагами.

Фактически прошли 58 backend-тестов, 368 assertions, включая потерю временного потока Redis и поздний heartbeat. Конкурентное выполнение нескольких recovery-процессов ещё не проверено.

## Постоянный consumer worker

Worker читает Redis Stream постоянно, восстанавливает неподтверждённые сообщения после 30 секунд бездействия и отправляет некорректные сообщения в ограниченный dead-letter stream без их содержимого. При потере Redis он переподключается. По умолчанию worker выключен: автоматические публикация outbox и восстановление по расписанию пока не подключены.

Фактически проверены 16 worker-тестов и сквозной сценарий с отдельной тестовой базой и временным Redis stream: восстановленная доставка и её дубликат дали один запуск, девять событий и ожидаемый CSV. Отдельной проверки длительной работы, сигналов остановки и переподключения ещё нет. Следующий шаг — безопасно связать dispatcher и восстановление с постоянным запуском.

## Автоматическая обработка очереди

Добавлен отдельный queue-manager: каждые пять секунд он выполняет ограниченную партию восстановления и отправки, продолжая работу при ошибке одного из двух действий. Профиль runtime включается явно и требует DATAFLOW_WORKER_ENABLED=1; ранее ожидавшие запросы при включении могут быть обработаны или получить QUEUE_TIMEOUT. Инструкция запуска обоих процессов — в README.

Проверены конфигурация Compose и 60 backend-тестов (378 assertions), включая порядок восстановления/отправки, независимость от ошибки и реальный Redis на временном потоке. Длительный совместный запуск queue-manager и worker ещё не проверен; кнопка запуска в UI остаётся отключённой. Следующий этап — изолированная сквозная проверка постоянных процессов, затем интерфейс запуска и результата.
