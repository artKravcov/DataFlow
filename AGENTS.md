# Правила работы над DataFlow

## Сначала контекст

Прочитай `PROJECT_CONTEXT.md`, `docs/MVP_SCOPE.md` и документы, относящиеся к текущей задаче. Осмотри существующий код и рабочие изменения до редактирования. Blueprint описывает целевое поведение, а не доказательство существования функциональности.

Следуй текущему запросу пользователя. Предложения v0.1 — исходные решения; обычные детали реализации выбирай самостоятельно. Если меняешь существенный контракт или границы MVP, объясни причину и обнови связанные документы/ADR. При противоречии, которое меняет смысл задачи, уточни только этот вопрос; независимую работу продолжай.

## Границы и структура

- `backend/`: Laravel API, авторизация, модели, планирование запусков, запись состояния.
- `frontend/`: Vue 3 + TypeScript, визуальный редактор, формы, история.
- `worker/`: Node.js + TypeScript, узлы, внешние системы, исполнение.
- `contracts/`: после появления кода — общие JSON Schema и примеры.
- `infrastructure/`: Docker и конфигурация окружения; `docs/`: документация.
- Не добавляй AI/MCP, Kafka, Kubernetes, marketplace, billing и микросервисы в MVP.
- Не реализуй весь roadmap по одному заданию. Заверши конкретный этап с проверяемым результатом.

## Инварианты реализации

Laravel проверяет membership и роль для каждой операции и каждого вложенного ресурса. Worker не пишет напрямую в БД приложения. Секреты не входят в граф, Redis, ответы браузеру, логи и фикстуры.

Запуск получает снимок графа. Сохранение графа атомарное, с проверкой revision. Сервер проверяет DAG, порты и принадлежность connections/assets той же организации. Клиентская проверка служит удобству и не заменяет серверную.

Не считай Laravel jobs совместимыми с Node-очередью без отдельного проверенного контракта. Учитывай повторную доставку. Не обещай exactly-once для записи во внешнюю систему. После неопределённого результата записи не выполняй автоматический повтор всего запуска.

Не исполняй пользовательский JavaScript, PHP, shell или произвольный SQL внутри узлов MVP. Следуй явным схемам конфигурации и ограничениям ресурсов.

## Работа и проверки

Используй существующие зависимости и принятые шаблоны. Не перезаписывай чужие изменения. Перед установкой закрепи совместимость версий; не используй плавающий `latest` в воспроизводимой среде.

Команды запуска и проверок бери из актуального README, Composer scripts и package scripts. Пока каркас не создан, таких команд нет: не сообщай о выполненных тестах. При создании каркаса добавь реальные команды в README.

Для backend изменений проверяй валидацию и tenant isolation; для графа — циклы/порты/revision; для worker — дубликаты доставки, падение и лимиты; для UI — сборку, типы и изменённый пользовательский сценарий. Полный перечень в `docs/QUALITY_AND_SECURITY.md`. Не создавай тесты, которые лишь повторяют реализацию.

Обновляй документацию вместе с контрактами. В конце кратко сообщи по-русски: что изменено, как проверить, что проверено фактически, какие ограничения остались, следующий разумный шаг. Объясняй незнакомые концепции на примере текущего изменения.

## Code Review Rules

Отмечай как ошибки: доступ между организациями; утечку credentials; изменение снимка запуска; повтор внешней записи после потери подтверждения; принятие устаревших worker events; отсутствие ресурсных лимитов. Не выдавай замечания по стилю за функциональные дефекты.
