# Продуктовый blueprint

## Задача

Данные разбросаны по файлам, API и базам. Для общего результата человек вручную выгружает части, меняет поля и переносит их в другое место. DataFlow сохраняет этот процесс как визуальный поток, который можно запускать повторно и наблюдать за его выполнением. Продуктовая позиция: **Schema-aware Visual Data Workflow Platform**, а не generic automation tool.

Ценность — воспроизводимая цепочка работы с понятными настройками, известной структурой данных и объяснимыми ошибками. Система должна помогать не только запустить шаги, но и понять, какие поля идут через pipeline, как они переименуются, валидируются и куда доставляются.

Короткая формула направления: **Connect → Understand → Transform → Validate → Deliver → Observe**. Это продуктовая гипотеза; сравнение с конкурентами и рыночный спрос пока не исследованы.

## Пользователи и сценарии

| Пользователь | Задача | Пример результата |
|---|---|---|
| Аналитик | Привести выгрузки к общей структуре | CSV заказов с одинаковыми именами полей |
| Разработчик | Передать данные между системами | Строки MySQL записаны в PostgreSQL |
| Маркетолог | Подготовить данные для анализа | Отфильтрованные кампании в таблице; рекламные коннекторы позже |

Одна платформа и одна модель графа для всех ролей. В перспективе — пользовательские интеграции и автоматизация разработки. Выполнение deployment-команд, управление инфраструктурой и изменение рекламы автоматически не входят в начальную версию.

## Основной путь

1. Войти, выбрать организацию, создать проект.
2. Добавить подключение или загрузить файл.
3. Создать pipeline, выбрать источник и увидеть ожидаемую или примерную schema Dataset.
4. Добавить блоки преобразований: Filter выбирает поле из входной schema, Map/Rename сопоставляет поля без кода.
5. Соединить блоки; увидеть причину недопустимой связи или неизвестной структуры.
6. Настроить получателя, сохранить и проверить граф.
7. Запустить вручную; увидеть очередь, текущий узел, результат и базовые data metrics.
8. При ошибке открыть проблемный узел, исправить конфигурацию или mapping и создать новый запуск.

## Интерфейс

Главная показывает текущие работы, недавние ошибки и последние завершения. После появления расписаний — следующие запуски. Количество запусков и длительность доступны в деталях, но не являются центром dashboard. Не показывать фиктивные проценты прогресса, когда объём неизвестен.

Редактор: каталог блоков слева, граф в центре, настройки выбранного блока справа. Для каждого поля — понятная подпись, пример и ошибка рядом. Названия вроде «Источник CSV» и «Переименовать поля» предпочтительнее внутренних type identifiers.

Pipeline Builder должен постепенно становиться schema-aware: показывать input/output schema узла, подставлять поля в Filter, помогать с visual field mapping и предупреждать о части несовместимых соединений до запуска. В раннем MVP допустимо состояние «структура данных пока неизвестна», если source не объявил schema и inference ещё не выполнен.

## Успех первой версии

Пользователь без редактирования кода собирает CSV → Filter → Map → CSV, получает ожидаемый файл и понимает причину намеренно вызванной ошибки. На этом пути Map работает как no-code field mapping: например `order_id → id`, `total → amount`. Второй пользователь другой организации не может прочитать ни граф, ни файлы, ни историю первого.

## Отличие от соседних продуктов

Это не маркетинговое доказательство уникальности, а рабочая рамка:

| Продукт | Основной фокус |
|---|---|
| n8n | Generic workflow automation: события, API-вызовы, действия между приложениями |
| Airbyte | Data movement / ingestion: перенос данных из sources в destinations |
| Kestra | Workflow/data orchestration: декларативные процессы, расписания, jobs |
| DataFlow | Visual schema-aware data workflows: typed datasets, mapping, transformations, validation, execution visibility |

DataFlow может пересекаться с этими категориями, но в MVP не пытается заменить их целиком. Акцент — визуальное проектирование data workflow, где структура проходящих данных является частью продукта.

После первого сценария провести несколько наблюдаемых проб с потенциальными пользователями: где неясна настройка, какие сообщения об ошибках непонятны, какие источники нужны следующими. Числовые цели конверсии и производительности устанавливать после этого, не придумывать сейчас.
