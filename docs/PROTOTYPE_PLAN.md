# План курсового прототипа

Этот документ фиксирует границу версии для сдачи курса. Он не заменяет [MVP_SCOPE](MVP_SCOPE.md), [ROADMAP](ROADMAP.md) или технические контракты: прототип реализует их первый вертикальный срез и оставляет полный MVP последующей работой.

## Цель демонстрации

Пользователь без написания кода собирает и запускает один линейный поток:

```text
CSV upload → Filter → Map/Rename → CSV download
```

Сценарий доказывает основную ценность DataFlow: данные действительно читаются из загруженного файла, преобразуются в отдельном Node worker и сохраняются как результат запуска. Авторизация, организации и проекты уже реализованы и поддерживают этот сценарий, но сами по себе не считаются основной функциональностью прототипа.

## Граница реализации

В прототип входят только следующие встроенные типы узлов:

| Тип | Назначение |
|---|---|
| `csv.source` | Читает приватный загруженный CSV asset |
| `transform.filter` | Оставляет строки по одному полю, оператору и значению |
| `transform.map` | Выбирает и переименовывает поля |
| `csv.destination` | Создаёт скачиваемый CSV result asset |

Граф линейный: один источник, до двух transform-узлов и один получатель. Пользователь настраивает узлы через формы, а не вводит JSON или код. Dataset v1 для CSV может считать все колонки строками; сложное schema inference не требуется.

Не входят в сдаваемую версию: PostgreSQL/MySQL/REST/JSON-коннекторы, credentials и connections, приглашения, расширенное управление ролями, fan-out, Cast, расписания, WebSocket, streaming, AI/MCP и marketplace. Эти возможности остаются в полном MVP или последующих этапах.

## Последовательность

| Шаг | Задачи | Проверяемый результат |
|---|---|---|
| P0 — граница | Документация | Этот документ согласован с T05–T10; M4 не реализуется ради сдачи |
| P1 — graph core | T05 | Pipeline и graph сохраняются атомарно с revision; сервер отвергает цикл, неверные порты и неизвестный тип |
| P2 — editor | T06 | Через UI собирается и сохраняется CSV graph без JSON/code input; reload сохраняет результат |
| P3 — assets | T07 | CSV upload сохраняет metadata и файл с лимитом; чужой asset нельзя прочитать или скачать |
| P4 — execution state | T08 | Run создаёт immutable snapshot, outbox и queued Execution; есть idempotency и один активный запуск |
| P5 — worker runtime | T09 | Redis доставляет задание Node worker; CSV реально фильтруется и преобразуется; output asset и статусы сохраняются |
| P6 — acceptance UI | T10 | UI показывает queued/running/succeeded/failed, скачивает результат и объясняет ошибку неверного поля |
| P7 — сдача | README и видео | Чистый локальный запуск описан; есть demo CSV и сценарий видео на 2–3 минуты |

## Обязательные инварианты даже в прототипе

- Laravel остаётся единственным писателем в БД приложения; worker изменяет состояние только через internal API.
- Каждая вложенная сущность проверяется на принадлежность организации и роль пользователя.
- Запуск использует неизменяемый snapshot graph revision.
- Сервер, а не только UI, проверяет graph, ports и revision.
- Files и output assets находятся вне web root; их скачивание авторизовано.
- Worker не получает secrets через Redis и не повторяет весь запуск автоматически после неопределённого внешнего результата.

Для CSV-only сценария secrets и внешние записи отсутствуют, но эти границы не следует обходить упрощением архитектуры.

## Контрольный пример

Входной файл:

```csv
order_id,status,total
101,paid,12.50
102,pending,8.00
103,paid,20.00
```

Настройка: `Filter(status equals paid)` и `Map(order_id → id, total → amount)`.

Ожидаемый результат:

```csv
id,amount
101,12.50
103,20.00
```

Это общая фикстура для backend validation, worker runtime, UI и видео. Полный разбор жизненного цикла находится в [EXECUTION_FLOW](EXECUTION_FLOW.md).

## Видео и материалы сдачи

Видео должно за 2–3 минуты показать: вход в локальное приложение, открытие проекта, загрузку входного CSV, настройку и сохранение graph, reload страницы, запуск, terminal status и скачивание итогового CSV. В репозитории должны быть понятные команды запуска, demo CSV и список фактически пройденных проверок. Внешняя ссылка на GitHub и ссылка на видео добавляются в материал сдачи после публикации.

## Правило ведения статуса

[ROADMAP](ROADMAP.md) хранит долгосрочную очередность, [FIRST_DEVELOPMENT_TASKS](FIRST_DEVELOPMENT_TASKS.md) — статусы T01–T10, а [PROJECT_CONTEXT](../PROJECT_CONTEXT.md) — фактические результаты последнего завершённого этапа. После каждого P1–P6 обновляются последние два документа; не нужно менять границу этого прототипа без явного решения.
