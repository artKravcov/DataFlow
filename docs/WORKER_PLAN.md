# План worker и доставки задач

Это предлагаемое решение v0.1. Оно сохраняет стек Laravel/Redis/Node, не требует совместимости сериализованных PHP jobs с Node. На этапе worker нужен небольшой интеграционный тест реального транспорта до добавления коннекторов.

## Транспорт

Redis Stream `dataflow:executions:v1`, consumer group `workers-v1`. Outbox dispatcher Laravel публикует JSON envelope:

```json
{"message_version":1,"message_id":"<outbox-uuid>","execution_id":"<числовой-id-строкой>"}
```

Outbox содержит этот минимальный envelope с UUID сообщения и числовым ID запуска, представленным строкой. Подготовлены общая JSON Schema, ограниченный publisher Laravel и parser worker; ограниченный dispatcher и интеграционная проверка контракта на настоящем Redis реализованы; автоматическая публикация доступна в явно включаемом профиле runtime. Никаких credentials, записей пользователя и полного графа в Redis. Получив сообщение, worker обращается к internal claim API. Laravel атомарно назначает owner запуска и lease. Только подтверждённый claim разрешает исполнение. Сторонние Laravel queues, если появятся для почты, используют отдельные ключи и не читаются этим worker.

## Публикация и восстановление

Execution и outbox создаются вместе. Реализованный dispatcher берёт ограниченную партию непубликованных записей с блокировкой `SKIP LOCKED`, публикует и отмечает `published_at`. При ошибке хранит следующую попытку с ограниченной задержкой; потерянное подтверждение может дать дубликат с тем же message_id. В профиле runtime публикация вызывается процессом queue-manager. Redis-соединение для потоков ограничено timeout.

Реализован ограниченный reconciler: queued execution без claim старше 30 секунд получает повторную отправку через тот же outbox с возрастающей задержкой до 60 секунд; уже ожидающую отправки запись не дублируют. После 10 минут ожидания запуск получает QUEUE_TIMEOUT. Если запись outbox отсутствует, она восстанавливается. PostgreSQL-блокировки SKIP LOCKED обеспечивают разделение строк между параллельными обработчиками. Команда также вызывается постоянным процессом queue-manager при включении профиля runtime.

Worker подтверждает stream message после успешного claim: дальнейшее состояние долговечно в PostgreSQL, recovery отвечает watchdog. Если claim занят/terminal — подтвердить дубликат. Если API недоступен — не подтверждать; повторно обработать pending через reclaim по idle timeout. Неизвестная message_version или повреждённый envelope — журнал инфраструктуры и dead-letter stream без секретов; пользовательская работа останется queued и будет перепроверена reconciler.

## Lease и события

Начальные параметры: heartbeat каждые 10 секунд, lease 60 секунд. API хранит hash lease token, worker хранит token в памяти. Просроченный token не может продлить lease или записать новое событие. Watchdog атомарно переводит просроченный running → failed с WORKER_LOST; текущий узел failed, pending узлы skipped.

Worker буферизует ограниченный набор событий и посылает последовательно, с event_id и sequence. Повтор после сетевого сбоя использует те же IDs. API подтверждает принятый sequence; worker не сообщает succeeded до подтверждения всех node results и фиксации output assets. Повтор финального события после потерянного ответа должен быть идемпотентным.

Если heartbeat не удаётся подтвердить до истечения lease, worker прекращает запуск следующих операций и пытается отменить текущую. Внешний запрос уже мог быть выполнен: lease не отменяет запись в чужой системе. Поэтому **потерянный running execution автоматически не запускается заново**. UI сообщает о возможных частичных изменениях.

## Runtime

1. Получить snapshot и проверенные credentials через claim.
2. Проверить поддерживаемые schema/type versions и лимиты.
3. Выполнить топологическую сортировку с устойчивым порядком по node ID среди готовых узлов.
4. Для каждого узла записать running, вызвать handler, проверить output Dataset/schema, записать succeeded и data metrics.
5. Освобождать промежуточные Dataset batches после последнего потребителя; весь запуск под общим byte/row budget.
6. При ошибке остановить дальнейшие узлы, передать безопасный error code/message и завершить failed.

Интерфейс handler концептуально: `execute(config, inputDataset, context) -> outputDataset | nodeResult`. Context содержит timeout/cancellation signal, ограниченный logger, resolver connections/assets и resource budget. Source не получает input и создаёт Dataset; transform возвращает новый Dataset со schema; destination возвращает metadata результата, не ещё один records port.

## Внешние эффекты

В MVP нет общего auto-retry. Чтение и запись имеют deadline. DB destination использует одну транзакцию на ограниченный набор; потеря подтверждения commit всё равно может оставить неизвестный результат. Upsert снижает риск дублей, но не гарантирует отсутствие повторных triggers. REST idempotency key допустим только если конкретный получатель документированно его поддерживает.

Ручной повтор создаёт новый Execution; интерфейс до отправки повторной команды поясняет, что внешние изменения могли сохраниться. CSV artifact публикуется как ready только после полной загрузки и checksum; частичный файл недоступен на скачивание. Загрузку идентифицировать парой execution_id + snapshot_node_id, чтобы повтор передачи не создавал второй результат.

## Проверки до расширения

Реальные Redis и Laravel/Node: повтор envelope, падение dispatcher после publish, потерянный claim response, недоступный API, истечение lease, позднее событие, повтор final event, потеря Redis, ошибка после успешной внешней записи. Ожидания описаны в [EXECUTION_FLOW](EXECUTION_FLOW.md).

## Промежуточная проверка контракта

[Redis envelope v1](../contracts/redis-envelope-v1.schema.json) содержит только версию, идентификатор сообщения и строковый числовой ID запуска. Изменение набора полей или версии требует согласованного обновления обеих сторон. Временная проверка публикует две копии фикстуры в отдельный поток с TTL 120 секунд, затем тестовый consumer group читает и подтверждает только эти тестовые сообщения. Она не запускает worker, не проверяет claim и не подключена к outbox. Интеграционная проверка выполнена на реальном Redis; её следует повторять при изменении контракта.

Проверка dispatcher на реальном Redis: `docker compose exec -T -e DATAFLOW_REDIS_INTEGRATION=1 backend php artisan test --filter=OutboxDispatcherTest`. Тест использует отдельную тестовую базу и отдельный временный поток; он не включает worker claim.

### Основа lease (без подключения worker)

Реализованы внутренние переходы состояния: только один claim переводит queued в running, токен хранится в базе в виде хеша, heartbeat продлевает только непросроченный lease, а проверка истёкших lease переводит запуск в failed с кодом WORKER_LOST и не перезапускает его. Claim и heartbeat доступны через internal API с сервисной авторизацией и повторной проверкой snapshot и готовности файлов; watchdog по расписанию не запускается. Контракт форматов и фикстуры добавлены, конкурентные обращения ещё не проверены. Утрата ответа claim намеренно не выдаёт новый токен при повторном обращении.

Internal API подключён только к backend в сети Docker. Постоянный consumer и процесс queue-manager реализованы и включаются явно.

Internal events реализованы частично: node.started/succeeded/failed и execution.failed, с проверкой порядка, lease и идемпотентным подтверждением. Успех destination и запуска требует готовый output asset с проверкой checksum; автоматические dispatcher, watchdog и reconciler доступны в профиле runtime.

Worker может получить входной CSV только через internal API и действующий lease. Передача CSV результата реализована: ограниченный поток с проверкой checksum и идемпотентностью по запуску и узлу. Успешное завершение после проверки результата подключено к internal events.

Реализована обработка одной доставки и запуск линейного CSV графа. Подтверждение Redis происходит после подтверждённого claim; при недоступном API или ошибке проверки snapshot сообщение не подтверждается. Сквозной тест использует отдельные test DB и stream с TTL и проверяет дубликат и итоговый CSV. Постоянный consumer восстанавливает pending после 30 секунд бездействия и отправляет некорректные сообщения в ограниченный dead-letter stream без содержимого сообщения. Он выключен по умолчанию; процесс queue-manager включается отдельно вместе с worker.

`dataflow:recover-executions --limit=25` однократно обрабатывает до 25 истёкших lease и до 25 ожидающих запусков. Подтверждённый running запуск после WORKER_LOST никогда автоматически не перезапускается. Для восстановления Redis существующую запись outbox возвращают в очередь отправки, сохраняя message_id; сам dispatcher следует вызывать отдельно. Процесс queue-manager вызывает восстановление и отправку каждые пять секунд; он включается профилем runtime только при DATAFLOW_WORKER_ENABLED=1. Длительная совместная проверка обоих контейнеров ещё не выполнена.
